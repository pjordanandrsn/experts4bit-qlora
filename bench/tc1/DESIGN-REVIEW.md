## Findings

1. **HIGH (Q5, Q1) — e4b's engagement predicate cannot detect the known loop fallback.** Draft L81: "e4b fused `n_patched == L`, `kernel_calls_per_step_min >= 2·L·A`". That counter counts entries into `nf4_qlora.fused_grouped_lora` (`tp4_reduce.py:194`, `tp4_arm.py:742`); P46 measured the `auto` rule sending ≥ 85 % of those calls to the per-expert Python loop at 24.46 s/step with the counter fully satisfied (`bench/p46/P46-PREREG.md` amendment 1; `RESULTS-tp4-p46cut.md` L5). gnf4's `lora_path_*` counters are already in the tc1 receipt (`tc1_arm.py:854`) but no predicate reads them. *Fix:* add to e4b fused validity `lora_path_loop == 0 on every step` (record the loop share beside kcalls); VOID otherwise.

2. **HIGH (Q4, Q5) — the step-0 ≤ 0.005 gate is mis-attributed and can VOID the comparator for a cause the lane leaves unmatched.** L81: "agree on step-0 held-out loss to 0.005 nats (same base, same init by construction)". With B = 0 and step 0 at lr 0 (L26), step-0 (and step-1) loss is independent of the init; what it measures is the quantiser bytes — exactly what F5 leaves unmatched (double-quant on attention). On this family the e4b-vs-Unsloth step-0 gap is on record at **0.0055** (P38, 3.7022 vs 3.6968), 0.0036 (tp2), 0.0001–0.0013 (tp4 field recipe). The harness brief registered 0.01 (`harness-brief.md:47-49`); the draft tightened it to 0.005 without a receipt. *Fix:* either match double-quant (F5) and keep 0.005, or restore 0.01; in both cases relabel the gate "same frozen bytes" and move the init check to F3.

3. **HIGH (Q1) — "same init" is never asserted across frameworks.** `init_sha` = sha over (parameter name, bytes) (`tp4_arm.py:578-583`), so the selftest can only assert fused == reference and hf == unsloth (`tc1_arm.py:2852`), never e4b == Unsloth; `matched_init.complete` is the overwrite code's self-report; the first init-sensitive reading is the step-2 train loss (steps 0–1 are at lr 0 → identical whatever A is). *Fix:* a name-free `matched_init_sha` over every A in canonical slot order (layer, kind, expert; fp32, [r, in]) in every receipt; the reducer VOIDs the matched set unless all its arms carry one sha; report |Δ train loss at step 2| as the init-takes reading.

4. **HIGH (budget, Q2) — the equivalence anchor is scheduled behind six arms and will not run.** L77 order: e4b_m, unsloth_m, e4b_d2, unsloth_d2, HF, axolotl m, *then* `e4b/reference_attn4_m`. Ceilings before the reference closes: 4×3600 + 1800 + 2700 (+2700 install) + 5400 ≈ 24,600 s against an 18,000 s guard, before the 61 GB fetch (~25 min at the 40 MB/s floor) and e4b's ~30-min prologue per e4b arm (TP4-PREREG amendment 5, L239). tp4's box C never reached its reference arm for exactly this reason (amendment 5). The step-0 VOID rule (L81) and the equivalence reading (L90) are both defined against the reference; if it is `host-limited`, P3 is unreadable and L111 forbids any position. *Fix:* run `reference_attn4_m` third, or split the lane into two draws (matched set + reference; labelled rows) — each $3.45 is inside the no-ask tier; and define the cross-framework equivalence against `e4b/fused_attn4_m` with the parity pair as the e4b-side control, so a missing reference degrades the reading instead of deleting it.

5. **MED (Q1, Q7) — the 4-bit regime is unmatched on double-quant, and the draft misreads axolotl.** L61: Unsloth "double-quant OFF if its loader takes a BitsAndBytesConfig"; the tp4 loader passes none (`tp4_arm.py:966`) and Unsloth's standard config has it on (UPSTREAM-NOTES L104-105: UNVERIFIED which config the MoE loader builds). L65: axolotl "double-quant forced True" — it is a *default when unset* (`upstream/axolotl-hf-stack.md:43`: `bnb_4bit_use_double_quant` unset → True), so it can be matched. Nested-absmax dequant is extra work and bytes for the arms that carry it (favours e4b in s/step and VRAM, slightly) and shifts step-0 bytes (F2). *Fix:* `bnb_4bit_use_double_quant: false` in the axolotl cfg; try `quantization_config=BitsAndBytesConfig(..., bnb_4bit_use_double_quant=False)` on `FastLanguageModel.from_pretrained` (record refusal if it is not accepted; the native-best arm keeps its default); the `frozen_base_probe` regime string ("+dq") is the assertion.

6. **MED (Q1, Q3, Q4) — attention implementation and loss kernel: neither matched nor recorded.** Unsloth's cu130 extra installs xformers 0.0.35 (`upstream/unsloth-2026.9.14.md:120`) and Unsloth patches attention and cross-entropy; e4b/HF run transformers' sdpa and fp32-upcast CE on torch 2.8. The receipt records `grad_ckpt` but not `config._attn_implementation`, the CE path, or `output_router_logits` (`tc1_arm.py`: no match). P3's bisection list names "attention implementation" (L100) but no receipt field can say what ran. *Fix:* record `_attn_implementation` (and Unsloth's chosen path), the loss class, `output_router_logits == False`, per arm; add torch/triton version to the P3 bisection list.

7. **MED (Q3) — torch 2.8 (e4b) vs torch 2.12.1+cu130 (Unsloth) is defensible as "what each installs here", but the equivalence reading now crosses torch, triton and transformers (5.18 vs 5.5.0) at once.** A DIVERGENT verdict could be a torch-version artefact and the bisection (L100) omits it; an e4b skeptic adds that e4b was never measured on the torch a Blackwell user installs (`_auto_install.py:44`, UPSTREAM-NOTES L82). *Fix:* one labelled control `e4b/fused_attn4_m_t212` in `venv-unsloth` (INSTALL_FAILED is a row); within 5 % of the torch-2.8 arm closes it.

8. **MED (Q3, Q7) — the "native-best" Unsloth arm is Unsloth's kernels under this harness's loop.** L69 adds only `UNSLOTH_MOE_RECOMPUTE=0` / `GC_REPLAY_PIN=1` and native init; no SFTTrainer, no packing/padding-free ("3x faster training & 30% less VRAM", `unsloth-2026.9.14.md:130`), no compiled trainer path. A maintainer will say the native row is not native. *Fix:* label arm 7 "native kernels, harness loop"; add a `loop: unsloth-trainer` row (SFTTrainer + packing, tokens/step recorded, never a matched position) in the shape the axolotl spec already has (`axolotl-arm-spec.md:39-41`), or state in the write-up that packing was not measured.

9. **MED (Q2) — dynamic padding × torch.compile inside the window.** L23: "right-padded to the longest row" per micro-batch → 80 distinct shapes over 20 steps. Unsloth compiles decoder code (its sparse block is `torch_compiler_disable_unless_decode`, `unsloth-2026.9.14.md:131`) and will recompile until the dynamo cache limit, then run eager — possibly inside steps 11–20. Not recorded. *Fix:* record `torch._dynamo.utils.counters` (recompiles, cache-limit hits) at steps 10 and 20 and the padded-length distribution per arm; recompiles inside the window → UNSTABLE.

10. **LOW (Q2) — what else is inside the window.** Every arm: a host sync per micro-batch (`float(out.loss.detach())`, `tp4_arm.py:1434`; same for all, but it forbids launch-ahead) and the PowerSampler thread (1.6 % in P38). Unsloth only: its checkpoint offload of each layer's input to pinned CPU (`unsloth-2026.9.14.md:110`) — at 2×2048 rows that is ~0.8 GB per micro-batch of PCIe traffic by my arithmetic, its own recipe; P38's `ckpt_hf` vs `ckpt_unsloth` (0.2 % apart) is a seq-512 receipt only. *Fix:* state both; a `unsloth/ckpt_hf_m` row if a draw has room.

11. **MED (Q2) — 10 steps × 2 draws is enough for the median; the 5 %/10 % rule is a non-control and the ratio is over-precise.** Same card class (tp2 qwen3, seq 512): steady-window IQR 3.2 % (e4b) / 1.8 % (Unsloth), half-window medians within 0.1–0.8 %; same-box draw-to-draw (P38): e4b 1.515/1.522/1.530, Unsloth 2.146/2.151/2.157 ≈ 1 %. The rule at L89/L99 will not fire, while a 4 % drift passes unflagged into "4.490". *Fix:* keep the rule; quote the position as the interval of the four cross-draw ratios (min, max) with the point; set Unsloth's tolerance to 5 % too (P8 predicts it is not host-bound on the grouped path).

12. **MED (Q4) — the equivalence bands have no receipt behind them and a different function passes them.** Same-function floor on record: e4b fused vs reference Δfinal 0.00063–0.00203 across four families (`RESULTS-tp4-p46cut.md` L26-30); paired held-out 0.0014–0.0047 at steps 20–60 (tp2/P38). A pair with UNMATCHED init and mixed precision read **0.0168** at step 200 (P38: 0.2881 vs 0.2713) — inside the 0.02 "EQUIVALENT" band — and 0.0283 at N = 20 (tp4) — inside COMPARABLE. So EQUIVALENT at 0.02 cannot separate "same function" from "the init effect, halved". *Fix:* tie the band to the in-draw floor: EQUIVALENT iff median per-step |Δ| and |Δ held-out| ≤ max(0.005, 3 × the fused-vs-reference Δ measured in the same draw); 0.02 → CLOSE; 0.05 → COMPARABLE; register the floor as a reading.

13. **MED (Q6) — 8 rows at N = 20: the mean only is recorded, so no SE, no sign test; the free noise floor is unused.** `eval_loss` returns `tot/n` (`tp4_arm.py:422-431`; `tc1_arm.py:486` unchanged). e4b's own forward is not run-to-run reproducible (gnf4 `index_add_` atomics): three same-box draws read 0.3459/0.3489/0.3504 at step 20 (P38) ≈ 0.005 nats. COMPARABLE at 0.05 is defensible as "not grossly different"; as a quality claim it is not. *Fix:* record per-row held-out losses; the reducer prints paired mean ± SE over rows and the row count favouring each arm; define the noise floor as max |d1 − d2| held-out within an arm and VOID any equivalence reading narrower than it. TC1b: per-row at every eval, paired SE at every eval; the claim is "no eval where the paired sign test favours either arm", not a 0.02 point band at 16 rows.

14. **MED (Q5) — C1's "byte-flip positive control on the same storage" (L81) is not what the committed code does, and C1 covers nothing of HF/axolotl's experts.** `control_flip_fires` flips one hex character of a digest string (`tp4_arm.py:435-442`) and `C1_control_detects_flipped_byte` is hard-coded `True` behind an assert (`:1581`): it tests dict comparison. The T21 `frozen_base_probe` does flip a copy of packed storage for three slots (`tc1_arm.py:1586`) — that is the real control. For non-e4b arms the hasher takes Params4bit and uint8 tensors only (`tp4_arm.py:493-509`), so bf16 expert stacks (HF's regime, and axolotl's parametrised stacks if they are not uint8-typed) are not hashed. *Fix:* hash every `requires_grad=False` expert stack regardless of dtype; print the hashed-tensor list; either replace the digest flip with one real byte flip on a copy of one hashed tensor or drop "on the same storage" from L81 for C1 and keep it for the probe.

15. **LOW (Q5) — the Unsloth backend-counter VOID (L49-51) has no reachable failing case under a forced backend.** `UNSLOTH_MOE_BACKEND=grouped_mm` makes the dispatcher raise if `_grouped_mm` is unsupported (`unsloth-2026.9.14.md:46`), so "counters show the loop when grouped_mm was requested" cannot happen; the silent fallbacks that remain are inside `forward_native_grouped_mm` — `_ManualGroupedMM` (489) and the per-expert matmul fallback of the LoRA delta on RuntimeError (L89-90). *Fix:* wrap `torch._grouped_mm` and require ≥ 6·L·A calls per step (base + 2 LoRA GEMMs × 2 projections); count `_ManualGroupedMM.apply`; arm 10's profile must list `_grouped_mm` kernels.

16. **MED (Q9) — host-boundness is profiled for Unsloth only.** L74/L93 profile arm 10 (Unsloth); e4b's device-busy fraction is not measured in this lane, though P45 found e4b's own field-recipe step host-bound (10.8 % GPU busy) before P46. `cpu_threads = os.cpu_count()` is recorded (`tc1_arm.py:469`) but torch's thread count is not set and the host CPU model is absent (the RunPod thread-thrash memory applies to any container that sees the host's cores). *Fix:* profile 3 steps of e4b with the same instrument; record CPU model and `torch.get_num_threads()`; set `OMP_NUM_THREADS` in the run script; the write-up states the ratio as a property of (card, host CPU, torch, fixture) measured on one host.

17. **HIGH (Q8) — the counterexample the campaign cannot see is the card Unsloth is built for.** Its grouped GEMM is "tested and benched on H100" (`unsloth-2026.9.14.md:91`); `torch._grouped_mm` is native on sm_90 even on torch 2.8; the 5090 is the class where the competitor's best path was unavailable until this lane. The ratio may shrink by a large factor on an H100 and no lane registers it; one matched-pair draw (~1 h) is inside the no-ask tier. Also missing: large rank (r 64/128 — the delta GEMMs grow and the padded path pads more); a bf16-resident competitor on a 48/80 GB card (out of scope by L121 — say so); Gemma-4, where e4b's own parity FAILED (#558, 0.09 nats), excluded as "no quality instrument at this resolution" (L121) — a skeptic reads that as excluding the family where e4b fails its own control. Registered and adequate: TC1b's t1 pair (small batch) and 200 steps; TC2 Mixtral (a footprint row, not a kernel comparison), gpt-oss (an e4b loss), granite/olmoe. *Fix:* register `TC1h`: the matched pair + reference on one H100, same fixture, same predicates; carry #558 beside the Qwen3 position in every write-up.

18. **LOW (Q7) — e4b runs a non-default speed flag; the others run defaults.** `enable_fast_train(dgrad=True)` — `dgrad` defaults to False and is "a second opt-in … a second numerics change" (`experts4bit_qlora/engines/fast.py:592-604`). e4b's attention-4-bit path is not a speed advantage on record (P38: bf16 attention 1.473 vs attn4 1.522 s/step). *Fix:* state in the arm table that `dgrad=True` is opt-in and e4b's default is not measured here (or add it as a labelled row); keep Unsloth's speed tilts in its native-best arm as planned.

19. **LOW (Q1) — "fp32 adapters" matches the master copy, not the forward arithmetic.** Unsloth casts A/B to the activation dtype every forward (UPSTREAM-NOTES L88); PEFT's fold runs `baddbmm` in W's dtype; gnf4's input dtype is not in the receipt. The 8-bit optimizer also quantises different memory layouts for B (PEFT `[out, E*r]` expert-fastest vs e4b's per-expert stack) — a legitimate, small noise source for F12. *Fix:* record the dtype the delta GEMM runs in per arm; say the match is of master weights.

20. **LOW (Q3) — zoo main is 10 commits ahead with `468efaf` (#1529, "never float32").** Not reachable under "bf16 compute, no autocast" per its description (`unsloth-2026.9.14.md:150`); pinning the released wheel is right. *Fix:* record the zoo commit and that the fix is not included.

21. **LOW (predictions) — P1b compares `ckpt_unsloth_t28` to tp4's 29.05 from another box (L98)**, which the lineage allows only for the labelled anchor (TP4 L9), and the t28 backend need not be tp4's loop: on torch 2.8 / triton 3.4 the dispatcher's default order is grouped_mm → unsloth_triton → native_torch and with bnb experts it "dequantises both stacks once … and runs grouped_mm / Triton / loop" (`unsloth-2026.9.14.md:49`), so the Triton grouped GEMM may engage where 2026.9.7 recorded `native_torch`. *Fix:* make P1b conditional on the recorded backend being `native_torch`; otherwise the row is a new measurement, not continuity.

22. **LOW (Q7) — HF gets no best arm in TC1.** On torch 2.8 its `grouped_mm` is the Python loop (L67); TC2 gives HF an `hf_best` on torch 2.14, TC1 does not. Immaterial only because P5 predicts OOM at load. *Fix:* if any HF row trains (e.g. `_mb1`), run it in the axolotl venv with `experts_implementation="grouped_mm"` too, or label the row "fallback loop by torch version".

23. **LOW (Q10) — what a systems reviewer rejects, and what the budget can answer.** n = 2 draws, 10 measured steps, one host, one card class, comparator on a different torch/transformers, 8 eval rows, bands with no registered floor, the author's own harness. Within budget: F4 (anchor first), F11 (interval), F12/F13 (floors from the draw), F16 (both arms profiled), F17 (one H100 pair). The write-up must also say what the matched ratio measures: kernel + dequant schedule + checkpoint mode + attention path + torch, not the expert kernel alone (TC1b's t1 pair is the only causal reading), and that Unsloth's 4-bit path is dequantise-then-dense-grouped-GEMM at the same NF4/64 bytes (UPSTREAM-NOTES L71-74) — the sentence a reader needs to interpret any ratio.

## Verdict

A skeptical expert could dismiss the position as designed, because (i) the one engagement predicate that protects e4b's number is satisfied by the fallback P46 already caught (F1), (ii) the two things this lane exists to fix — matched init and matched regime — are not actually asserted across frameworks (F3) and are not actually matched on double-quant (F5), with the step-0 gate mis-attributed to the init and tightened past a measured 0.0055 gap (F2), (iii) the equivalence anchor is scheduled where tp4's history says it will not run (F4), and (iv) the whole campaign stays on the one card class where the competitor's intended path was unavailable, with no H100 row (F17). None of these needs a new lane or more than ~$4: a `lora_path_loop == 0` predicate, a name-free init sha, `bnb_4bit_use_double_quant=False` in two configs, the reference arm third, per-row eval losses, an interval instead of a point, and one H100 matched pair. With those, the remaining objections are the honest ones the write-up can state (one host, 10 steps, 8 rows, the author's harness), and the position could not be dismissed on its design.
