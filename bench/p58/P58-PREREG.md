## Why this lane exists

The register's only current-vs-current comparison against a production engine is P37's **vLLM 0.28.0 vs e4b's NF4 control** — not the stack anyone would serve. Since P37: e4b moved to the RTN int4 experts + uncalibrated int4 attention + K16 route + fused q/k/v stack (P42 → P54, register rows `e4b.serve.p54.*`), and vLLM shipped **0.29.0 (2026-09-09; Model Runner V2 default, CUDA-graph memory profiling for KV sizing, batch-sharded sampling)** and **0.30.0 (2026-09-22, today)**. The brief (`reference_local_ml_systems_briefs_2026_09`) says: re-run the identical-prompts head-to-head before any serving position is quoted against vLLM. This lane does that, for both vLLM builds, on one box, in one session.

**Two vLLM builds, stated up front.** The owner asked for 0.29; 0.30.0 was released the morning this was registered. The **PRIMARY** vLLM arm is the **latest PyPI release at launch** (0.30.0 unless `P58_VLLM_PRIMARY` pins it — "current vs current" means the field's current) and the **SECONDARY** is **0.29.0 pinned** (`P58_VLLM_SECONDARY`). Each gets its own venv, its own tripwire, its own graph_r1/graph_r2 pair; the reducer quotes a ratio per build and the build-to-build delta. If the two resolve to the same version the secondary rows are skipped. If 0.30.0 fails to install on the sm_120 image (P37's 0.28 needed a ≥ 12.9 toolkit; 0.30 may need more), its rows read `vllm_init_failed`/`PIP FAIL` and the 0.29.0 rows carry the lane — a vLLM install failure cannot void the e4b arms (P37's order).

## Verdict rule (pre-registered; the lane's product is a POSITION, not a pass/fail)

1. **VOID arm** (never enters a ratio; the row says why): an e4b receipt without `step_ms_clean`, with recompiles in the window, with the wrong step count (127/70), or failing its engagement rule above; a vLLM receipt without graph capture on a graph arm (or with capture on the eager arm), returning fewer tokens than asked, or with a `prompts_sha256` different from the e4b side's.
2. **Self-pair rule:** a ratio is quoted only when both sides' self-pairs are inside **1.03×** (`nf4_r1/r2`, `int4_r1/r2`, and that build's `graph_r1/r2`); outside it the row reads **DRIFT**, both readings are printed and **no ratio is quoted as a position**.
3. **The number, per vLLM build and batch size:** `ratio = vllm_decode_tok_s(graph_r1, min-of-3 slope) / e4b_tok_s(int4_r1)`, three decimals, both absolutes beside it, the median-of-3 slope, the `int4_r2` variant and the vLLM/NF4-control ratio beside. `> 1` = vLLM ahead. Plus the **build-to-build** line `vLLM primary / vLLM secondary` per batch.
4. **Three axes for e4b's arm** every time it is quoted: ×N over the same-box NF4 control, rental-measured tok/s (and ms/step) on this box with the host named, and at B=1 only the anchor-class PROJECTION `159.2 × ratio`, marked projection. P54's medians are cited beside (STOP-1 informational at ±8 %), never divided into.
5. **Register:** rows `e4b.serve.h2h.vllm-<primary-version>.qwen3.5090.2026-09-<dd>` and `…vllm-0.29.0…` (measured; conditions naming every knob, the checkpoint revisions, the int4 stack's env, the prompts digests) plus per-arm rows in P37's shape; `e4b.serve.h2h.vllm-0.28.0.qwen3.5090.2026-09-05` stays as measured history (not superseded — a different e4b stack; cited beside). STATUS and the serving-throughput position doc are re-pointed at these rows; the old "×1.47 / ×1.55" and the NF4-control-only ratios are labelled historical.
6. **Quality is quoted, never equated** (P37 rule 5). **Same box, same session, identical prompt ids** — the only ratio this lane produces (P37 rule 1). **FAIL stays FAIL, DRIFT stays DRIFT** — a second lane is a second lane.

## Predictions (falsifiable; written before the data, with the standing correction that vLLM has been under-called twice — estimates biased UP)

- **P1 — vLLM 0.30.0 (or whatever is latest) at B=1: ahead of e4b's int4 stack, ratio 1.02–1.20 (central 1.10).** vLLM 0.28 read 286.0 tok/s on P37's box and ~283 on two others (B=1 is engine-launch-bound and reproduces across hosts); 0.29/0.30's runner changes are not B=1 decode levers on a Marlin GPTQ model, so 280–310 tok/s. e4b's int4 B=1 stack read 3.693 ms = 270.8 tok/s on P54's box; on a slower host 250–275. *Refuted by* e4b ahead (ratio < 1.0) or vLLM ahead by more than 1.25×.
- **P2 — vLLM at B=16: ahead, ratio 1.35–1.75 (central 1.52).** vLLM 0.28 read 2030 on P37's box (2172 on P20's fair re-run); the 0.29 batch-sharded sampling and the 0.30 runner may add 0–8 % → 2050–2300. e4b's B=16 unfused int4 stack read 11.420 ms = 1401 tok/s on P54's box; host-bound, so 1300–1450 here. *Refuted by* a ratio under 1.25 or over 1.9.
- **P3 — build-to-build: vLLM 0.30.0 vs 0.29.0 within ±5 % at both batches** (neither release note names a decode lever for a Marlin GPTQ dense-attention MoE at these shapes). *Refuted by* > 5 % either way — which would itself be the finding to record.
- **P4 — eager pairing (secondary):** vLLM eager 0.06–0.10 of its graph arm at B=1 (P37: 0.073); e4b eager 0.04–0.08 of its graph arm (P37 lic_eager 0.052); eager-vs-eager between 1.3 and 2.2 (P37 1.705). Never the headline.
- **P5 — instrument:** self-pairs inside 1.03× on all three pairs per batch; e4b int4 / NF4 same-box ratio ×2.3–2.7 at B=1 and ×2.4–3.0 at B=16 (P37's NF4 read 113.4 / 500.1; P54's int4 stack 270.8 / 1401 on another box — a projection, informational); STOP-1 within ±8 % of P54's medians.
- **P6 — prompts/tokens (recorded, not a gate):** the two engines' continuations from identical ids diverge within 128 tokens on most rows (different quantisers).

## Decision rule (what changes on which outcome)

Nothing in this lane changes a default. Its outputs are (a) the register rows and the re-pointed serving-throughput position, with vLLM's version pinned and the e4b stack's env recorded; (b) the build-to-build delta, which tells the next comparator lane whether pinning 0.29 vs latest matters; (c) if P1 is refuted in e4b's favour at B=1 that is quoted only as "on one box with one prompt set" (memory: a same-box result is never a general position); (d) if the B=16 ratio exceeds 1.75 the next B=16 lever work (attention + lm_head + glue, per `finding_samebox_h2h_vllm`) is the priority over any further B=1 fusion.
