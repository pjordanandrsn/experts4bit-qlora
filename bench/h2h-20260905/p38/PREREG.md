### Verdict rule per arm and the reading, pre-registered before any data

This lane has no PASS/FAIL between frameworks; it produces a **position table** in registered units. What it does decide per arm is whether the arm may be read at all:

1. **VOID** (no verdict, the row says why) if any of: `trainable_params ≠ 321,257,472`; a trainable parameter outside the adapters (router, norms, embeddings — the census names it); `tokens_sha` ≠ the file's; e4b `fused*` arms with `n_patched ≠ 48` or `kernel_calls_per_step_min < 96` (2 × 48: the fused forward did not reach the kernel on some layer); e4b `*attn4` arms with `n_attn_4bit ≠ 192`; Unsloth arms whose 4-bit census shows < 96 `Params4bit` expert stacks, or whose backend line is missing / names a non-bnb4bit path, or whose `moe_bnb4bit_calls_per_step_min < 48` (the expert forward did not go through the 4-bit MoE backend on every layer — a silent fallback to a bf16 or native loop is exactly the "green skipped path"); C1 not clean (bit-exact false, 0 bytes, empties > 0, control silent) in that arm; a different step count than registered.
2. **e4b internal parity, informational** (tp1 owns the licence): `e4b_fused_attn4` vs `e4b_reference_attn4` in the flagship's B2/C2 units — |Δ final train loss| ≤ 0.05 AND median step-wise |Δ| ≤ 0.05 — printed as PASS/FAIL beside the cost ratio, never changing anything in this lane.
3. **Cross-framework reading threshold, not a gate:** the two primary arms' held-out losses at step 60 (and at every shared eval) are printed with their difference; **|Δ| ≤ 0.05 nats reads "comparable quality"**, outside it the cost ratio is printed WITH the loss delta beside it ("faster at a different loss") and **time-to-TARGET decides** the comparison the directive asks for.
4. **The numbers, primary pair (`e4b_fused_attn4` vs `unsloth_ckpt_unsloth`, N = 60):** `s/step ratio = unsloth / e4b` (median 11..60; > 1 = e4b faster), peak VRAM both (GB, allocator peak; nvidia-smi max beside), tokens/s both, J/step both (with the perturbation caveat if it fires), held-out loss at 0/20/40/60 both, time-to-0.32 both (from the 200-step arms if not reached by 60), adapter bytes both. Secondary rows: `e4b_fused` (bf16 attention) and `unsloth_ckpt_hf`, same columns, labelled secondary. No "best" tally, no winner rule beyond the printed numbers.
5. **No cross-box, no cross-lane ratio.** tp1's Qwen3 rows (a different box of the same class) and the 2026-08-26 numbers are cited beside with their dates; the flagship's 4090 rows likewise.
6. **The claim.** `e4b.train.h2h.unsloth.p38.qwen3-30b.5090.<date>` (measured-private; conditions = every fixture line above + both versions); the 2026-08-26 memory's "1.17× ahead" is marked superseded-as-a-comparison by this lane whichever way it falls.

### Pre-registered predictions (falsifiable; the competitor estimate is biased UP per the standing correction)

- **P1 — both frameworks run the registered configuration on 31.8 GiB.** e4b: 20.0 GB resident after load (tp1's Qwen3 load row), training peak 22–26 GB (dgrad-gate resident 23.1–25.5 on seq 512 with bf16 attention; attn4 −1.3 GB); Unsloth: 21.6 GB peak at seq 192 × mb 4 (2026-08-26) → lower at batch 1.
- **P2 — peak VRAM: Unsloth lower by 1–4 GB** (double-quant, every Linear 4-bit incl. whatever its skip list leaves, offloaded checkpointing in the primary mode).
- **P3 — s/step: Unsloth FASTER per step at this workload, by 1.3–3× (central 2×).** Reasoning: at ≈ 100 tokens per step and batch 1 the e4b step is launch- and host-bound (48 layers × per-expert LoRA + HF checkpointing + fused kernels at tiny M; tp1's Qwen3 reference read 12.8–13.0 s/step at its snapshot; the flagship ratio fused/reference ≈ 1.78 → e4b fused ≈ 5–8 s/step), while Unsloth's dequant + `grouped_mm` amortises per layer (2026-08-26: 4.33 s/step at 3,072 tokens/step → 2–4.5 s/step here). This inverts the 2026-08-26 1.17× (which was the arena path at 3,072 tokens/step). **If e4b comes out ahead, that is the finding, not a reason to re-run.**
- **P4 — tokens/s** follows s/step (same tokens per step in both arms).
- **P5 — J/step:** the faster arm has the lower J/step; no prediction on power draw beyond that.
- **P6 — quality:** step-0 held-out loss differs by < 0.02 between frameworks (same bytes, both NF4 block 64; double-quant is nearly free); at step 60 within the 0.05 reading threshold; the e4b fused-vs-reference pair passes its band (tp1's Qwen3 pair should agree).
- **P7 — adapters:** identical parameter count (asserted) and identical fp32 bytes ≈ 1.285 GB on both sides (321,257,472 × 4 B) plus format overhead; if PEFT/Unsloth writes bf16, ≈ 0.64 GB — a format difference, reported as such.
- **P8 — time-to-0.32:** reached by both inside 200 steps; the arm with the lower s/step reaches it first unless the curves separate (P6 false), in which case this metric — not s/step — is the comparison quoted.
- **P9 — Unsloth checkpoint modes:** "unsloth" mode 1–3 GB below HF mode at ≤ ±10 % s/step (no strong prior on the sign).
- **P10 — step-time assumptions (alarms only, replaced by measurements):** e4b reference_attn4 ≈ 12–14 s, fused(_attn4) ≈ 5–8 s, Unsloth ≈ 2–4.5 s per step.

### Reading rules (pre-registered)

1. **Registered units only:** s/step, tok/s, GB, J/step, loss in nats; no "%" positions, no floor, no projection (P36 rule 3: training has no anchor class).
2. **Same box, same session, identical tokens** — the only ratios this lane produces.
3. **Engagement before reading.** e4b's arm shows the same engagement as tp1 (`enable_fast_train` 48 patched, the kernel counter ≥ 96/step, and for attn4 the 192 NF4 projections); Unsloth's arm shows its own banners (`Enabling LoRA on MoE parameters`, the `Unsloth: MoE bnb4bit …` backend line, 96 `Params4bit` expert stacks, ≥ 48 backend calls/step). **A green skipped path is not evidence** on either side; a missing banner is VOID.
4. **A refusal is a row.** `refused` / `oom` / `load_fault` / `alarm` / `verify_failed` / `void_*` appear in the table with the framework's other arms and the message; the workload is never weakened to make a row appear.
5. **FAIL stays FAIL; VOID stays VOID.** No re-registration out of dissatisfaction; a second lane is a second lane.
6. **Quality beside speed, always.** No s/step ratio is quoted without the same-step held-out losses beside it; when they differ by > 0.05, time-to-TARGET is the headline.
7. **Nothing here licenses anything** — not e4b's paths (tp1 does that) and not Unsloth's; the claim is a position with two versions pinned.
8. **Every receipt carries `tokens_sha`, `trainable_params`, the 4-bit census, `init_sha`, the box class and the instance id**, so the table can be checked without the box.

### Failure classes and what each writes

`PIP FAIL (e4b)` / `TRIPWIRE FAIL (e4b)` → `TP_DONE`, exit 9 (nothing measured). `PIP FAIL (unsloth)` / `TRIPWIRE FAIL (unsloth)` → the e4b arms still run; the lane writes `NO COMPARATOR` and the Unsloth rows read `install_failed` with the pip/tripwire tail (a one-sided lane is not an H2H; the e4b rows are still tp1-class receipts on this box). `DUD BOX` (10), `BOX_REFUSED` by the train anchor (12, re-rent), `DATASET MISMATCH` (13), `TOKENS MISMATCH` (14: the tokenised file's sha does not reproduce), `DL FAIL` (11). Per arm: exit 0 receipt; 3 `refused`; 4 `C1 FAIL` (receipt written, arm void); 5 `oom`; 6 `load_fault`; 7 `verify_failed`; 15 `void_trainable` (param count); 142 (SIGALRM) → the run script writes an `alarm` stub. Every arm's result line goes to `summary.txt`; `RESULTS.txt` / `RESULTS-p38.md` are `p38_reduce.py`'s; `TP_DONE` is touched last.
