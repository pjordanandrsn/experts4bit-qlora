### Fixture

**Model and checkpoints (revisions pinned; the tripwire refuses any other).** Both engines serve Qwen3-30B-A3B (48 layers, 128 experts top-8, hidden 2048, expert intermediate 768, vocab 151,936, no tied embeddings).
- e4b: `Qwen/Qwen3-30B-A3B` @ **`ad44e777bcd18fa416d9da3bd8f70d33ebb85d39`** (bf16, 30.5 B parameters, 16 shards; `snapshot_download` with `revision=` pinned) → NF4 arena by `k8_bake.py` (bo7's), then the hook builds the int4 packs at arm start (streamed GPTQ, `E4B_CALIB_NSEQ=128` = 32 batches × 4 × 512 = 64k C4-validation-shard-00000 tokens, damping 0.01, `min_rows=32`, 24 GiB Hessian budget, GPU solve) and the C4-calibrated int4 attention pack (192 projections, `calib.json`).
- vLLM: `Qwen/Qwen3-30B-A3B-GPTQ-Int4` @ **`9b534e4318b7ebc3c961a839f13eb18b1833f441`** (Qwen's official release: `quant_method gptq`, **4 bits, group_size 128, sym, desc_act false, damp 0.01, true_sequential**; `torch_dtype float16`; one 16 GB safetensors file; 29.9 B parameters packed I32 + 0.64 B in F16 = embeddings, lm_head, norms, routers). vLLM resolves it to `auto_gptq` → `MarlinLinearKernel` for the dense projections and the `MARLIN` WNA16 MoE backend for the experts (P20's log; the lane asserts the same lines or records what replaced them).

**Why this comparator and no other.** (a) It is the checkpoint P20 measured, so the *engine* delta is the only new variable on the vLLM side. (b) It is the same 4-bit class as e4b's arm: 4-bit weights on attention AND experts, 16-bit activations, a calibrated quantiser on both sides. The differences are disclosed, not equated: e4b packs experts as int4-b32 (32-wide groups, ~4.5 bits/weight incl. scales) calibrated by e4b on C4-validation shard 00000 and attention as C4-calibrated int4-b32; Qwen's GPTQ pack is g128 (~4.13 bits/weight) calibrated on Qwen's set; e4b's KV cache is fp8 paged, vLLM's default is fp16 (`kv_cache_dtype=auto`) — hence the fp8-KV vLLM arm below. (c) `Qwen/Qwen3-30B-A3B-AWQ` does not resolve on the Hub as of 2026-09-05 (401 on the model API — "HF 401 ≠ repo exists": not proof either way, but not a checkpoint this lane can pin), so there is no official AWQ arm. (d) **A bf16 reference arm does not fit**: 30.5 B × 2 B = 61 GB of weights against 31.8 GiB; vLLM cannot load it single-card and neither can e4b's paged path — no bf16 arm, stated here so its absence is not read as an omission. (e) Quality is *quoted, not equated*: e4b's arm carries the register's K8 licence (bo6c: wikitext −0.053 / c4val1 −0.066 ppl vs same-cut NF4, both sub-floor; NF4 itself 0.00173 nats from the model's own attention on Qwen3); the GPTQ checkpoint carries whatever its author measured on the model card — this lane scores neither and equates nothing.

**Prompts — one file, both engines, identical token ids.** P20's two sides used the *same corpus and window length* but not the same ids (vLLM's rows were 4,096 tokens apart by `h2h_vllm_wt.py`; e4b's rows are `step = (N − 512) // B` apart by `step_decomp._k8_window`). P37 makes them identical: the lane imports the staged `step_decomp.py` and calls its own `_k8_window` (wikitext-2-raw-v1 **test**, non-blank lines joined by `\n\n`, tokenised with the base checkpoint's tokenizer *with* special tokens, `--ppl-source wikitext`, no offset/span) at B=1 and at B=16, writes `prompts_b1.json` / `prompts_b16.json` (row ids, per-row sha256, file sha256, distinct-row count) and the vLLM driver feeds those ids verbatim as `prompt_token_ids` (vLLM's `TokensPrompt`) — no tokenizer runs on the vLLM side. Row 0 of the B=16 set is the B=1 prompt (`i = 0` in both). Rows are ≥ 18k tokens apart in a ~300k-token corpus, i.e. different articles (the rule of 2026-09-03: natural distinct text per row, never offsets into one passage); the driver asserts `len(set(rows)) == B`. Both receipts carry the file sha; the reducer refuses a ratio whose two sides do not agree on it. The routed-experts census the 2026-09-02 rule asks for is **not taken** (vLLM's `enable_return_routed_experts` changes the engine path; e4b's `--router-probe` is a separate mode): identical greedy prompts exclude the identical-row collapse by construction, and that is what the rule exists to catch.

**Decode isolation, both sides (the P20 protocol, unchanged).** 512-token prompt, **128 generated tokens, greedy**, context 640 within `max_model_len 2048`.
- e4b (bo7's protocol verbatim): `step_decomp.py --model Qwen/Qwen3-30B-A3B --arena … --calib calib.json --placement-override all-vram --amort off --batch B --prompt-len 512 --gen-tokens 128 --b1d-loop graph --b1d-timed --no-fuse-qkv` — B=1: prefill through the scheduled path, a short warm, ONE step captured and replayed, **127 timed steps**, no per-step sync, wall = window / N (`B1D_TIMED_GRAPH steps=127 step=X ms`); B=16: `BV3_GRAPH batch=16 steps=70 … agg=Y tok/s` (aggregate over 70 graph steps). fp8 paged KV; `E4B_RECOMPILE_LIMIT=64`, `E4B_ACCUM_RECOMPILE_LIMIT=64`, bo7's `fenv all` = `E4B_FUSE_T1_GLUE=1 E4B_FUSE_T1_GLUE_R2=1 E4B_FUSE_ROUTER_EPI=1`, `E4B_SERVE_EXP_INT4=1 E4B_SERVE_ATTN_INT4_CALIB=1 E4B_SERVE_EXP_INT4_CALIB=1 E4B_CALIB_SOURCE=c4 E4B_CALIB_NSEQ=128 E4B_INT4_GPTQ_DEVICE=cuda`, `PYTHONPATH=/root/p37/hook`. tok/s at B=1 = 1000 / step ms (rounded to the 0.01 ms the logs print, bo5/bo7's convention); at B=16 = the receipt's `aggregate_tok_s`.
- vLLM: **offline `LLM.generate`**, the slope method: generate 32 and 128 tokens from the same prompts (`temperature 0`, `ignore_eos`, `min_tokens = max_tokens`, `seed 0`), one untimed warm at each length, 3 timed repetitions each, `decode_ms_per_step = (min wall_128 − min wall_32) / 96` (P20's estimator, kept for continuity; the median-of-3 estimator is printed beside it), `decode_tok_s = 96·B / (wall_128 − wall_32)`, and `end_to_end_tok_s_long` (128·B tokens over the 128-token wall, prefill included) as before. Prefill, engine scheduling of the prompt and load cancel in the slope; per-step scheduling and detokenisation do NOT cancel, so vLLM's number includes its serving loop while e4b's replay window has no scheduler — as P20 noted, the asymmetry understates vLLM's engine, it does not inflate it. Why offline and not the OpenAI server: the server adds HTTP + client concurrency + tokenisation to one side only; the offline generate is the same engine core with the same scheduler and the same CUDA graphs, and it is what P20 measured. Why not vLLM's own per-step metrics: they are engine-internal; the slope needs no internals and applies to any engine.
- **Synchronisation:** e4b syncs once around the window (`--b1d-timed`); vLLM's `generate` returns after every output is complete. Both are wall-clock per token over the timed window.

**vLLM serving knobs (every one recorded in the receipt from `llm.llm_engine.vllm_config` and the engine log).** `dtype auto` (→ float16 from the checkpoint config; bf16 is available on sm_120 but `auto` is the engine's own choice and P20's), `max_model_len 2048`, `gpu_memory_utilization 0.90`, `max_num_seqs` default (256; recorded), `quantization` auto-detected (gptq → Marlin), **`enable_prefix_caching=False`** (P20 left it at the default True; with the 32- then 128-token runs on the same prompt the cached prompt KV would cancel in the slope anyway, but the directive says off, so off), `speculative_config=None`, `tensor_parallel_size 1`, `seed 0`, `disable_log_stats`, compilation at the default (`VLLM_COMPILE` + inductor; the `torch.compile` cache dir is fresh on this box), chunked prefill at the default, **`kv_cache_dtype`** and **`enforce_eager`** per arm (table).

**CUDA-graph policy — both run, and which is the comparable arm.** e4b's licensed protocol is the graph loop (one captured step replayed; the eager loop is the identity reference, `--b1d-loop eager`). vLLM's default is `cudagraph_mode FULL_AND_PIECEWISE` (full decode graphs at the captured batch sizes, incl. 1 and 16). **The comparable pair is vLLM default-graphs vs e4b graph loop** — both engines at their captured-decode best, which is how each is served. `--enforce-eager` is run as a secondary vLLM arm so the graph contribution is on the record for both engines (e4b's eager loop at B=1 is the secondary on our side), never as the headline.

**Peak VRAM (both sides, two instruments).** A 1-s `nvidia-smi --query-gpu=memory.used` sampler brackets every arm (`vram_<arm>.txt`, max and at-load); vLLM additionally reports its own accounting line (`Actual usage is X GiB for consumed memory (weights + non-torch), Y GiB for peak activation, and Z GiB for CUDAGraph memory` + `Available KV cache memory`) — vLLM's `memory.used` is a *policy* number (it reserves 0.90 of the card up front), so the comparable figure for vLLM is weights + activation + graphs from its log, with the reserved KV pool stated beside it; e4b's `memory.used` max is its footprint (arena + packs + fp8 KV + graph pool) and the harness's `hybrid tier active … masses` line names the placement.

**TTFT — defined, judged not fair, recorded but not compared.** TTFT = wall from request submission to the first generated token. vLLM's offline API exposes no per-request TTFT without its metrics path, and e4b's timed harness runs the prompt through the chunked scheduler (`--chunk 128`) before the window with a `PREFILL tokens=… wall=…ms` line that is a scheduled prefill wall, not a request-level TTFT. Neither is the other's instrument. Both numbers are pulled into the receipt where they appear, labelled *informational*, and **no TTFT ratio is quoted**. A fair TTFT needs both engines behind the same request path (server + client) — out of scope, named.

### Verdict rule, pre-registered before any data

This lane has no PASS/FAIL: its product is a **position** — the ratio vLLM / e4b, decode tok/s, per batch size, from the primary pair — and the rule says when a ratio may be quoted at all.

1. **VOID arm** (no number enters a ratio; the row says why) if: e4b — the run log lacks `INT4EXP … 48 layers (qwen3_moe)` **and** `ATTNINT4 192 projections` **and** the streamed-calibration line whose pack counts read **11512 gptq / 776 rtn** (bo6b's, bo6c's and bo7's counts for the 64k pack — host-independent; a different count is a different pack), or `recompiles_in_window ≠ 0`, or `fuse_qkv ≠ false`, or `n_steps ≠ 127` (B=1) / `70` (B=16); vLLM — the log lacks the Marlin kernel lines for the GPTQ path (or the engine names a different kernel: recorded, and the arm is `KERNEL-CHANGED`, still quotable as *vLLM as shipped* with that label), the graph arm lacks `Capturing CUDA graphs` or the eager arm has it, `got != n_tokens·B` (the driver asserts every row generated exactly `max_tokens`), or the receipt's `prompts_sha` differs from the e4b side's.
2. **Self-pair rule.** A ratio is quoted only when both sides' self-pairs are inside **1.03×** (`e4b_nf4_r1/r2`, `e4b_lic_r1/r2` at B=1, `vllm_graph_r1/r2`); outside it the row reads **DRIFT**, both readings are printed and **no ratio is quoted as a position** — a re-run is a new lane, not a re-registration. (P20 ran its e4b arms twice and matched to 0.01 ms; vLLM reproduces across boxes to ~1 %.)
3. **The number.** Per batch size: `ratio = vllm_decode_tok_s(vllm_graph, min-of-3 slope, r1) / e4b_tok_s(e4b_lic_r1)`, printed to three decimals with both absolutes, the median-of-3 slope beside the min, and r2 beside r1. `> 1` = vLLM ahead. Secondary rows print the same way, labelled secondary.
4. **The instrument check, reported not gated:** `e4b_lic / e4b_nf4` on this box must be quoted beside bo7's ×2.067 / ×2.602 — inside ±10 % (the class dispersion + host-boundness) it is *reproduced*; outside it the lane says so and the H2H ratio still stands (the H2H does not depend on bo7).
5. **Three axes for e4b's arm** (rule 3 of P35): ratio ×N over the same-box NF4 control, rental-measured tok/s on this box (with host CPU named), and — at B=1 only — the anchor-class projection `159.2 × ratio`, marked PROJECTION (the class was never certified; no projection exists at B=16).
6. **Supersession.** The bundle registers `e4b.serve.h2h.vllm.p37.qwen3.b1.5090.<date>` and `.b16.…` at tier **measured-private** (this tree) with `conditions` naming vLLM's pinned version and every knob above; `e4b.serve.h2h.vllm.same-box` gets `status: superseded` pointing at them, its `evidence_private` and the P20 receipts untouched. STATUS/README lines that quote 1.47×/1.55× as the *current* position move to the new numbers; the old numbers stay as history with their date.

### Reading rules (pre-registered)

1. **Same box, same session, identical prompt ids** — the only ratio this lane produces. No number from bo7, P20, or any other box is divided into a p37 number; they are cited beside, with their boxes and dates.
2. **Engagement before reading.** e4b's licensed arm must show the same banners as bo7/tp1 (`INT4EXP`, `ATTNINT4`, the streamed-calibration pass lines with the 64k counts); an arm without them is VOID, never a slower-than-expected data point. vLLM's arm must show its kernel selection lines; a silent fallback (e.g. a non-Marlin GPTQ path, a different attention backend) is recorded in the row's label.
3. **A green skipped path is not evidence.** A vLLM arm that returns fewer tokens than asked, an e4b arm with recompiles in the window, a pre-flight that reads exactly 0 — each is an instrument fault (P20's list) and the row says so.
4. **FAIL stays FAIL; DRIFT stays DRIFT.** No re-registration out of dissatisfaction; a second lane is a second lane.
5. **Quality is quoted, never equated.** e4b's arm is licensed by the register's gate on two texts; vLLM's checkpoint carries its author's evaluation; this lane scores neither and never says "at equal quality".
6. **The old numbers are historical.** ×1.47 / ×1.55 remain true as measured (0.27.0/0.21.0 vs vLLM 0.28.0, 2026-09-03, box 49702459) and are cited as such; the new claim ids carry the current position with vLLM's version pinned at launch.
7. **Three axes** for e4b's arm every time it is quoted; vLLM's number is quoted with its version, the checkpoint revision and the arm's knobs.
8. **Every receipt carries `prompts_sha`, the box forensics, and the engine versions**; the reducer refuses to divide two receipts with different `prompts_sha`.

### Out of scope (stated so it is not read as omitted by accident)

No K8 or logprob scoring of the vLLM checkpoint (no registered instrument for another engine; a `prompt_logprobs` NLL through vLLM is a LATER item); no OpenAI-server / client-concurrency measurement (TTFT stays informational); no other batch sizes, prompt lengths or context lengths; no other checkpoints (AWQ, FP8, bf16 — the first does not resolve, the other two do not fit); no llama.cpp / SGLang / TensorRT arms (the 02-plan's three-way is a separate lane); no tuning of either engine beyond the knobs listed (P20's "tune all or tune none"); no anchor-class certification; no gate change anywhere.

### Failure classes and what each writes

`PIP FAIL (e4b)` / `TRIPWIRE FAIL (e4b)` → `TP_DONE`, exit 9 (nothing measured; re-rent or fix). `PIP FAIL (vllm)` / `VLLM IMPORT FAIL` → the e4b arms still run to a receipt, the lane writes `NO COMPARATOR` and `TP_DONE` (exit 20/21): a one-sided lane is not an H2H and is not quoted as one. `DUD BOX` (10), `DL FAIL` (11), `BAKE FAIL` (12), `PROMPT DUMP FAIL` (13 — the two engines cannot be fed the same ids; nothing runs), `SLOW BOX` at pre-flight (re-roll, launcher side). Per arm: exit 0 receipt; 142 (SIGALRM) → the run script writes an `alarm` stub; a vLLM engine-init failure → `vllm_init_failed` stub carrying the last `Engine core` / `CUDA` line of its log (the 2026-09-02 lesson: grep the real reason before calling it a box fault). Every arm's result line goes to `summary.txt`; `RESULTS.txt` / `RESULTS-p37.md` are `p37_reduce.py`'s; `TP_DONE` is touched last, after the reducer, so the marker means "the table exists".
