# P60 — where the expert GEMV's B=16 headroom goes: real routing, recorded and replayed through the shipped kernel (registered 2026-09-22, before the run)

Owner directive (Jordan, 2026-09-22): *"go on"* — the throughput list, next item. Record: [#652](https://github.com/pjordanandrsn/experts4bit-qlora/issues/652), [#564](https://github.com/pjordanandrsn/experts4bit-qlora/issues/564). Predecessors: **P57 amendment 3** (`bench/p57/RESULTS-p57.md`): at B=16 the router touches **58.7 distinct experts per layer per decode step**, so #564's byte roofline for the expert GEMV is **4.89 ms/step** against the measured **6.34 ms** `_gemv_int4_b32` row — ~77 % of roofline, **~1.4 ms/step** of headroom in the largest row of the 11.6 ms step. **P23** (`finding_gemv_plan_microbench_refuted_by_real_routing`): a GEMV config sweep on UNIFORM expert ids chose configs that lost 0.892× in serving; the shipped config's small per-program slices get L2 reuse across rows of hot experts. So any read of this kernel must replay the workload's recorded routing, and must first reproduce the served row.

## Question

At B=16 each expert-GEMV call runs R = 16 × 8 = 128 activation rows, but only ~59 distinct experts: the kernel's grid (`cdiv(N, 128) × R × SK`) streams each row's expert slice once per row, so a hot expert's bytes are read from L2 (or HBM) once per row routed to it. Is the 1.4 ms the cost of those **repeated rows** (then a grouped kernel reading each expert once for all its rows is the lever), of **row order** (repeats far apart in the launch miss L2), or of the **per-expert kernel** itself (below roofline even with one row per expert)?

## Instrument (built and dry-run before registration)

1. **[`record_eids.py`](record_eids.py)** — the served int4 stack (P54's: RTN int4 experts, uncalibrated int4 attention, K16 route, glue r1/r2; `E4B_FUSE_ROUTER_EPI=0` so the router module is called) built by P44's `serve_stack`, on the 16 wikitext rows every B=16 lane decoded (`prompts_b16.json`, digest `f67e7e4d…`): prefill 384 tokens in 8-token-per-row chunks (128 rows per forward, the harness's step), then **128 decode positions at B=16, teacher-forced**. A forward hook on every MoE router records the routed ids of every 16-row call host-side (no graph capture on this path). Output `eids [128 steps, 48 layers, 16, 8]`. CPU self-test (tiny Qwen3-MoE): prefill chunks excluded by row count, every decode call recorded.
2. **[`replay_gemv.py`](replay_gemv.py)** — grouped-nf4-gemm only: synthetic int4-b32 weights for 128 experts at Qwen3-30B-A3B's expert shapes (gate_up N 1536 K 2048, down N 2048 K 768; bytes and cache behaviour depend on which experts a call touches, not on the values); for each recorded step, its **96 expert-GEMV calls** (48 layers × gate_up + down) captured into one CUDA graph and replayed 20× (median). Arms: **served** (R = 128, routing order, gnf4's own plan — the instrument), **sorted** (the same 128 rows ordered by expert), **dedup** (one row per distinct expert — the load-side lower bound for any kernel that reads each expert once), **floor** (distinct bytes ÷ this box's measured device-to-device bandwidth; #564's 1,528 GB/s floor beside it). The kernel row is read with `torch.profiler` over graph replays on the first 8 steps — the census's own instrument. Dry run on the QNAP A2000: both self-tests pass (dedup rows bit-equal served rows of the same expert), all arms capture and replay, the profiler finds `_gemv_int4_b32`; the reducer's instrument gate correctly FAILS on the A2000's numbers (a card 12× slower than the 5090 row), so the gate is live. A2000 timings are not evidence and are not quoted.

## Predictions (written before the data)

- **P0 — instrument (gate):** the served arm's `_gemv_int4_b32` time is within **± 15 % of P57's 6.340 ms/step**. If not, the replay does not reproduce the served kernel's work and **nothing below is read**.
- **P1 — repeated rows are the cost:** `served − dedup ≥ 0.8 ms/step` (central ~1.2: R 128 → ~59 per call; if loads dominate the kernel, dedup approaches the floor). *Refuted by* < 0.3 ms — then a grouped kernel's ceiling is too small to build.
- **P2 — one row per expert is near roofline:** `dedup / floor ≤ 1.15`. *Refuted by* > 1.30 — then the per-expert kernel config is a lever of its own.
- **P3 — row order does not matter:** `|sorted / served − 1| ≤ 3 %`. Reason: with split-K 16 on `gate_up` each pass touches ~59 × 98 KB ≈ 6 MB of distinct weights, far below the 5090's L2, so repeats already hit cache whatever their order. *Refuted by* > 3 % either way (a favourable refutation is itself a cheap lever).
- **P4 — routing reproduces:** mean distinct experts per layer per step within **58.7 ± 3** (P57's greedy-generated count; this one is teacher-forced on the same rows).

## Decision rule

**¬P0 → nothing is read** (instrument fault recorded). **P0 ∧ P1 → a grouped expert GEMV (one weight read per expert for all its rows, K16-style M-tiling over the rows routed to it) is licensed to BUILD** — pre-registered as grouped-nf4-gemm lane K18 before any code, with bitwise-or-K6 correctness gates and its own 5090 read. **P0 ∧ P3 refuted favourably → a consumer lane orders rows by expert once per layer** (one argsort per layer, shared by gate_up and down) and reads it in the step. **P0 ∧ P2 refuted → the per-expert config is re-examined on recorded ids** (the P23 lesson: never on synthetic ones). **P0 and none of P1/P2/P3 → the headroom is not where this lane looked**, stated as such. Nothing here changes a default.
